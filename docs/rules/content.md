# 학습 콘텐츠 규칙

## 콘텐츠 구성

각 학습 트랙은 `언어/프레임워크 → 주제 → 학습 단위 → 문항`으로 탐색할 수 있어야 한다. 학습 단위에는 목표, 선수 지식, 난이도, 예상 시간, 설명, 예시, 연습, 해설, 관련 단위를 포함한다.

- 각 트랙의 학습 순서는 번호가 있는 3개 이상의 단계로 나누고, 단원 번호와 선수 단원 관계를 기록한다. 학습자는 순서를 이해할 수 있어야 하며, 점수로 다음 단원을 잠그지 않는다.
- 장기 학습 경로는 **최소 26주**·주 5회 학습을 기준으로 구성한다. 주차마다 구체적인 5일 목표·짧은 설명·예제와 하루 3개의 서로 다른 연습 문제를 둔다. 주제 범위와 선수 관계상 더 긴 과정이 필요하면 26주보다 늘릴 수 있으며, 짧은 구간을 전체 언어 숙달로 표현하지 않는다. 단계나 구간은 실제 주차의 묶음이다.
- 기존 문항 ID를 유지할 때는 문제의 정답 의미와 선택지 ID/문구 연결을 바꾸지 않는다. 교육과정 확대 과정에서 과거 완료 기록과 현재의 주간 완료 기준을 구분한다.
- 신규 트랙은 값/기초 문법에서 조건·반복, 함수·자료구조, 객체/프레임워크 흐름처럼 선수 개념부터 쌓는다. 프레임워크 단원은 필요한 언어 개념을 명시한다.
- 화면에 보이는 진도·단원 수·이어하기 위치는 실제 카탈로그와 로컬 기록에서 계산한다. 새 트랙은 첫 문제로 바로 보내기 전에 단계 개요를 보여 준다.

## 문항 유형

- 객관식: 질문·선택지·정답·오답별 설명을 제공한다. 보기의 위치만 외워 정답을 맞히지 못하게 트랙 안에서 정답 위치를 균형 있게 섞는다. 기존 답안 기록과 백업을 위해 보기 ID와 그 ID가 가리키는 문구의 연결은 바꾸지 않는다.
- 주관식: 기대 개념과 허용 가능한 답의 기준을 제공한다. 초기 자동 평가는 단순·명확한 정규화 규칙에 한정하고, 모호한 답은 기준 답과 비교해 스스로 확인할 수 있게 한다.
- 오류 찾기: 오류가 있는 줄 또는 코드 범위, 잘못된 이유, 수정안을 함께 설명한다.
- 코드 수정·리팩터링: 시작 코드, 요구사항, 제약, 예시 입출력, 테스트 기준, 힌트 단계를 명시한다.
- 별도 코딩 문제 은행은 `src/coding-problems.js`의 검수 가능한 데이터와 `scripts/coding-problem-schema.mjs`의 자동 검사를 사용한다. 학습자 예제와 채점 공개 사례를 분리하고, 실행 가능 상태는 실제 등록된 로컬 어댑터와 일치해야 한다. 정적 배포의 테스트는 공개 데이터이며 숨은 테스트라고 표현하지 않는다.
- 무료·정적 환경에서 프레임워크의 실행 환경이나 안전한 채점 경로를 제공하기 어려우면 실행형 문제 은행을 억지로 추가하지 않는다. 대신 버전 맥락을 확인한 코드 읽기·오류 원인 찾기·설계 선택·요청 흐름 분석 문제를 제공할 수 있다. 이런 문항과 코드 예제는 실행·컴파일·테스트를 마친 것처럼 표시하지 않으며, 지원하지 않는 기능은 화면과 문서에서 분명히 구분한다.
- 개념 카드·짧은 복습: 한 번에 하나의 목표를 다루고, 정답 확인 뒤 설명을 제시한다.

## 품질 기준

- 모든 문항에는 하나의 학습 목표와 검토된 정답 기준이 있어야 한다.
- 풀이는 정답을 반복하는 데 그치지 않고 근거를 설명한다.
- 코드 예제는 별도 명시가 없으면 완결된 최소 예제이며 언어와 버전 맥락을 적는다.
- 프레임워크 문제는 어떤 버전 또는 일반 원칙에 관한 것인지 표시한다. 공식 문서를 참조한 날짜나 링크가 필요한 주제는 출처를 기록한다.
- 버전 기록은 해당 날짜의 공식 안정판/LTS와 호환 범위를 검증해 적는다. draft, preview, 비-LTS, 미지원 버전은 안정 기능과 혼합하지 말고 화면에서 그 상태를 밝힌다. 동적으로 바뀌는 버전 주장은 출처와 재검토 날짜를 함께 둔다.
- 모든 선택지는 학습 목표와 일관되어야 하며 정답뿐 아니라 오답 판단의 이유도 설명한다. 오류 찾기 정답 줄은 실제 코드 결함과 해설의 수정안을 가리켜야 한다.
- 객관식에는 의미가 중복되는 보기나 둘 이상 정답으로 해석될 수 있는 보기를 두지 않는다. 오답은 질문에 답이 되지 않는 이유를 설명하고, 정답 기준은 자동 검사와 실제 예제를 대조해 확인한다.
- 실행 환경이 없는 언어의 코드 수정 자동 채점은 문항별 전체 함수·메서드 구조 패턴으로 제한하고, 패턴이 없으면 정답 처리하지 않는다. 부분 문자열 포함 여부만으로 정답 처리하지 않는다. 구조 패턴 검사는 코드를 실행하거나 동작을 검증한 것처럼 표현하지 말고, 허용하는 형식과 범위를 화면에 설명한다. 실행/호환성 검증이 없는 프레임워크 예시는 개념 스니펫임을 분명히 한다.
- 결과 실행 문제는 문항의 함수 계약과 공개 입력 사례를 코드 반환값 기준으로 검수한다. stdout을 기대값으로 사용하는 경우는 출력 자체가 학습 목표일 때만 별도로 선언한다. 모든 공개 사례가 통과한 사실만으로 임의 입력에서의 정답을 보장한다고 안내하지 않는다.
- 코딩 문제 계약 검증은 문제 ID·선수 관계·필수 학습/버전/출처/검수 정보·입출력 값의 JSON 안전성·테스트 개수와 크기·실행 어댑터를 검사한다. 함수 반환은 타입과 중첩 값을 비교하고, 배열 순서는 유지하며, 객체 키 순서는 무시한다. 허용 오차나 문자열 정규화는 문제별 필요와 실제 실행기가 함께 검증된 경우에만 추가한다.
- 오답 설명과 힌트는 답을 너무 일찍 노출하지 않으면서도 막힌 사용자가 다음 시도를 할 수 있도록 한다.
- 미검증 콘텐츠는 공개 완료로 표시하지 않는다. 콘텐츠 리뷰 여부를 진척 관리에 남긴다. 자동 검사는 데이터 구조·정답 키·사례 실행 같은 확인 가능한 속성을 증명할 뿐, 설명·예제·문항이 학습 목표에 맞는다는 편집 검수를 대신하지 않는다. 주차를 편집 승인하기 전에 목표→설명→예제→문항→정답·해설의 연결을 실제로 확인하고 감사 범위와 근거를 기록한다.

## 표현

- 용어를 처음 쓸 때 짧게 풀어 설명하고, 언어별 표기 관례를 따른다.
- 안내·예제·문제·해설은 초보자도 편하게 읽을 수 있는 존댓말 해요체로 쓴다. 번역투나 관리자 말투를 피하고, 꼭 필요한 기술 용어는 쉬운 말로 먼저 설명한다.
- 화면 문구에서는 `탐색`, `학습 경로`, `학습 단위` 같은 딱딱한 표현을 줄이고 `배울 주제`, `과정`, `수업`처럼 익숙한 말을 쓴다. 짧은 버튼은 `보기`, `골라보기`, `이어 풀기`처럼 다음 행동이 바로 보이게 한다.
- 초보자를 탓하는 표현을 쓰지 않는다. 오답은 다음 시도를 돕는 중립적인 피드백으로 표현한다.
- 출처가 있는 내용을 그대로 복제하지 말고 자체 설명과 예제로 가르친다. 라이선스를 확인할 수 없는 문제 세트를 가져오지 않는다.
